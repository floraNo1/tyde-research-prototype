# TYDE 研究原型

这是从最初 TYDE 产品代码中独立提取出的研究核心。它研究一个具体决策问题：长期运行的
Agent 收到一条新信息后，应该判断它是否值得长期保存、保存到哪里，以及它是否应该改变
下一步行动。

完整英文研究说明、架构、案例与结果见 [README.md](README.md)。

## 核心研究问题

1. 哪些信息应该成为持久状态或长期记忆？
2. 状态变化应该怎样影响下游行动？
3. Agent 怎样在保留未来规划所需信息的同时避免错误写入？

## 一键复现

```powershell
python demo.py
python -m examples.run_cases
python -m evaluation.evaluate --fail-on-mismatch
python -m unittest discover -s tests -v
```

以上命令均从仓库根目录运行。不需要 API key，也没有第三方 Python 依赖。

## 核心机制

```text
新的用户交互
  ↓
  意图识别 / 项目路由
  ↓
  选择性更新策略
  ↓
  当前状态 / 未来生效状态 / 项目状态 + 项目记忆
  ↓
  判断是否影响计划
  ↓
  下一步行动
```

研究原型只保留五个可运行模块：

- `router`：区分闲聊、状态更新、偏好和项目更新；
- `state`：维护当前有效状态、未来生效状态和项目状态；
- `memory`：隔离项目并保存有来源的长期信息；
- `updater`：决定忽略、替换还是持久化；
- `planner`：检验更新后的状态是否真正进入下一步行动。

## 三个关键 case

1. 今天从广州变成香港：旧地点被替换，planner 只能使用香港；明天才生效的地点则进入
   `scheduled_state`，不会提前覆盖今天的位置。
2. “昨晚电影很好看”：不进入长期记忆，状态版本不变化。
3. 论文截止日期变化：只修改对应项目，并触发使用新日期的计划修订。

## 受控诊断测试

诊断集一共 35 条，覆盖状态新增、状态替换、稳定偏好、无关对话、项目变更、跨项目噪声，
以及地点习语和非法日期等 hard negatives。
这些 case 的用途是作为当前 state/update contract 的可执行规格，而不是自然语言理解 benchmark。
当前透明参考策略全部通过，false-write rate 为 0；诊断还单独检查未来状态没有提前覆盖
当前事实。

这个结果只证明实现满足手工诊断规格；规则和样例是共同设计的，因此不能当作真实语言理解准确率，
更不能声称 SOTA。下一步应冻结接口与测试集，换入不同 LLM router，再用独立改写的 held-out 数据比较。

## 与产品代码的边界

这个目录不包含前端、商业 API、真实数据、用户交互记录、内部 prompt、账号系统或生产数据库。
原来的大产品可以继续作为未来用户实验的外层载体，但 GitHub 上用于申请和学术展示的核心，
可以只展示这里这套可读、可跑、可评估的 research artifact。
